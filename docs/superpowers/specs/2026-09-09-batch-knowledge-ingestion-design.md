# 批量知识入库与目录解耦设计

日期：2026-09-09

状态：待用户书面设计复核

## 背景

当前知识入库是面向单文件的四步向导：解析正文、确认属性、预览索引、最终入库。它适合精细处理单份重要文档，但批量导入时每个文件都要重复操作，人工时间随文件数量线性增长。

当前界面还容易让用户把“知识目录”理解成上传和解析的前置条件。实际上，目录用于人工浏览整理；正文解析、分块和向量索引由文档用途及分块配置决定。将两者绑定，会造成“必须先建目录还是先上传”的无效决策，也会让目录调整看起来像需要重新解析。

本设计在保留单文件精细入库能力的同时，增加面向效率的批量路径，并明确文件处理、目录整理、索引和发布之间的职责。

## 已确认目标

1. 首要目标是提高多文件入库效率，避免每份文件重复走完整向导。
2. 支持从知识库首页快速上传，也支持从某个知识目录内上传。
3. 目录不是上传、正文解析或 AI 分析的前置条件。
4. AI 提供标题、用途、目录和其他元数据建议；用户在集中审核后统一确认。
5. 自动处理正常项，把人工注意力集中到缺少必填属性、AI 分析失败、解析失败等异常项。
6. “待整理”是系统筛选视图，不创建同名真实目录。
7. 调整目录不触发正文重解析、分块或向量重建；调整参与文档简介索引的标题和普通元数据时，只更新文档级向量，不重做正文抽取和分块。

## 非目标

本阶段不实现：

- 多知识库或 Dataset 实体；
- 原始文件与多个知识库的多对多关联；
- 人员、角色和目录权限；
- 独立标签管理体系；
- 索引版本历史、回滚和多 Embedding 空间；
- 断点续传、跨浏览器恢复和独立后台任务系统；
- 对现有检索排序、MCP 工具和向量维度的调整。

出现多套权限或索引策略、同一文件确需进入多个检索空间，或者批量任务需要关闭浏览器后继续执行时，再分别设计上述能力。

## 领域职责

| 概念 | 当前承载方式 | 职责 |
|---|---|---|
| 原始文件 | 预览目录中的临时原件，入库后保存到 documents 目录 | 保存用户上传的原件 |
| 解析结果 | 预览中的 `parsedText`，入库后进入知识文档 | 保存正文抽取结果，供分块复用 |
| 知识文档 | `knowledge_documents` | 保存标题、用途、目录、状态和业务元数据 |
| 知识目录 | `knowledge_categories` 与可空的 `category_id` | 供用户浏览和整理，不决定能否解析 |
| 文档用途 | `knowledge_purposes` | 决定整份模板能力、正文分块能力和默认分块配置 |
| 索引 | 文档向量与 `knowledge_chunks` | 支持模板推荐、正文检索和重排 |
| 发布状态 | `draft`、`effective`、`obsolete` | 决定文档是否进入 AI 检索 |

本阶段不把这些概念机械拆成七张新表。现有模型已经能表达第一阶段需要的边界，优先复用。

## 目录与系统视图

### 真实知识目录

真实目录继续用于人工导航，可以新增、重命名和移动。文档的 `category_id` 允许为空。

- 从某个目录点击上传：新文件默认带入当前目录。
- 从知识库首页点击上传：目录默认为空，解析和 AI 分析照常进行。
- 审核时可以接受 AI 推荐目录、选择已有目录或保持未分类。
- 审核时允许通过现有目录创建能力新建目录；创建成功后回到审核上下文并自动选中。
- 修改文档目录只更新 `category_id`，不重新抽取、分块或生成向量。

### 系统筛选视图

知识库导航增加与真实目录视觉上分组的系统视图：

- 全部文档；
- 待整理：`category_id IS NULL`；
- 草稿：`status = 'draft'`；
- 已发布：`status = 'effective'`；
- 已废止：`status = 'obsolete'`。

批量任务中的“解析失败”和“需要确认”只属于当前入库任务状态，不混入永久知识目录。第一阶段不为这些视图增加数据库实体。

这些系统视图直接基于前端已经取得的文档列表计算和筛选，不新增统计接口。

## 两条入库路径

知识库页面继续保留一个“上传文档”主入口。文件选择器开启原生多选：选择 1 个文件时进入现有单文件精细流程；选择多个文件时进入批量快速流程。这样不增加上传前的模式选择步骤，也不破坏现有单文件操作习惯。

### 单文件精细入库

保留现有四步流程，用于需要逐块检查和编辑的重要文档：

1. 解析正文；
2. 确认属性；
3. 预览并编辑索引分块；
4. 最终确认并入库。

### 批量快速入库

新增批量路径，默认面向多个普通文档：

1. 选择多个文件；
2. 以受控并发逐份上传并解析正文；
3. 对解析成功的文件执行 AI 元数据分析；
4. 根据用途的默认配置生成索引预览；
5. 在一张审核表中集中检查结果；
6. 用户选择要入库的文件并执行一次批量确认；
7. 逐份建立索引，成功项立即完成，失败项保留以便重试。

第一阶段由浏览器编排现有逐文件后端接口，不新增常驻队列服务和批量任务数据库。正文解析和 AI 分析阶段固定最多同时处理 2 个文件，最终索引阶段逐份处理，防止同时压垮 Docling、元数据模型和 Embedding 服务。页面明确提示处理期间不要关闭入库弹窗。只有实际压测证明服务端具备余量时，后续才提高并发或增加配置项。

## 批量审核模型

每个文件独立维护以下状态：

- `waiting`：等待处理；
- `parsing`：上传和正文解析中；
- `analyzing`：AI 元数据分析中；
- `ready`：必填数据完整，可以入库；
- `needs-review`：正文存在，但 AI 分析失败或必填数据不完整；
- `indexing`：最终建立索引中；
- `completed`：入库成功；
- `failed`：解析或最终入库失败。

不使用模型自报的百分比作为自动通过依据。`ready` 由系统可验证规则决定：

- 正文解析成功；
- AI 返回结构有效；
- `purposeId` 对应现有用途；
- 标题等通用必填字段完整；
- 用途允许生成模板时，模板家族完整；
- 用途包含正文检索能力时，至少存在一个有效分块。

`ready` 项默认勾选，用户仍需点击一次“确认并入库”完成整批确认。`needs-review` 和 `failed` 项默认不勾选，并优先展示。目录为空本身不属于异常，因为目录不是发布条件。

## 批量审核界面

批量上传弹窗采用任务列表，而不是把单文件四步表单复制多份。

顶部展示总数和状态汇总：

```text
已选择 27    可入库 21    需确认 4    失败 2
```

列表每行至少展示：

- 选择框；
- 文件名；
- 标题；
- AI 建议用途；
- 知识目录；
- 当前处理状态；
- 错误或需要确认的原因；
- “检查详情”与“重试”操作。

批量操作只覆盖明确需要的能力：

- 修改目录；
- 修改文档用途；
- 重新分析失败项；
- 删除尚未入库的任务项。

“检查详情”复用现有元数据表单和分块预览能力，允许编辑单个文件。关闭详情后回到原批量列表，并保留处理进度和已选项。

## 目录创建交互

目录选择控件包含“新建目录”操作，但它不是上传前置步骤。

1. 用户在单文件详情或批量修改目录时点击“新建目录”。
2. 复用现有目录创建表单，输入目录名称和上级目录。
3. 创建成功后刷新目录选项，返回原审核上下文。
4. 新目录自动成为当前文档或所选文档的目录。

本阶段不引入目录审批和权限限制；人员权限功能设计时再限制可创建层级。

## 处理与发布时序

批量流程先完成正文解析、AI 分析和分块预览，最终确认后才调用现有索引接口生成向量并保存正式文档。因此：

- 未确认文件不会进入 AI 检索；
- 无效 AI 建议不会自动发布；
- 用户取消任务时可删除所有尚未入库的临时预览；
- 已成功入库的文件不会因为同批其他文件失败而回滚；
- 重试只处理失败项，不重复提交成功项。

这是逐项提交而非整批数据库事务。批量任务的目标是提高吞吐与人工效率，不要求所有文件同时成功或同时失败。

## 修改触发规则

| 用户操作 | 重新抽取正文 | 重新分块 | 文档级向量 | 分块向量 |
|---|---:|---:|---:|---:|
| 修改目录 | 否 | 否 | 否 | 否 |
| 修改标题、关键词、摘要或模板属性 | 否 | 否 | 是 | 否 |
| 修改发布状态 | 否 | 否 | 否 | 否 |
| 修改用途，但新旧用途索引能力和分块设置相同 | 否 | 否 | 是 | 否 |
| 修改用途，导致索引能力或分块设置变化 | 否 | 是 | 是 | 是 |
| 修改分块规则或分块内容 | 否 | 是 | 否 | 是 |
| 修改解析器或 OCR 配置 | 是 | 是 | 是 | 是 |
| 替换原始文件 | 是 | 是 | 是 | 是 |
| 修改 Embedding 模型 | 否 | 否，可复用现有分块 | 是 | 是 |

在现有系统中，标题、用途名称、文档类型、关键词、模板属性、适用场景、摘要、正文目录和部分解析正文共同组成文档级索引内容。编辑这些字段时更新文档级向量，是搜索一致性要求，不等同于重新抽取正文或重新生成分块。

## 接口与代码边界

第一阶段优先复用现有 REST 合同：

- `POST /api/knowledge/preview`：上传单个文件并抽取正文；
- `POST /api/knowledge/previews/{preview_id}/analyze`：生成 AI 元数据建议；
- `POST /api/knowledge/previews/{preview_id}/rechunk`：生成分块预览；
- `POST /api/knowledge/previews/{preview_id}/index`：确认并建立正式索引；
- `DELETE /api/knowledge/previews/{preview_id}`：放弃临时预览；
- 现有知识目录增删改接口：在审核上下文内创建目录。

AI 目录建议需要对分析接口做一项向后兼容扩展：后端把当前目录 ID、名称和完整路径作为允许值交给元数据模型，响应新增可空的 `suggestedCategoryId`。模型只能返回现有目录 ID；返回空值或无效 ID 时按“未分类”处理，不因此阻塞入库。现有调用方忽略新增字段时行为不变。

现有文档更新接口在修改前后 `document_profile` 内容相同时复用原文档级向量。这样目录和发布状态调整不会发起无意义的 Embedding 请求；参与文档简介索引的字段发生变化时仍更新文档级向量。

前端代码继续位于 `frontend/js/features/knowledge/`：

- `upload.js` 保留单文件入口和公共弹窗生命周期；
- 新增聚焦批量任务编排的业务模块；
- 元数据表单、分块预览和目录选择继续复用现有业务模块；
- 只有真实出现两个业务域共同需要的逻辑才进入 `ui` 或 `core`。

后端继续由 `documents` 域负责文档生命周期，`catalog` 域负责目录和用途；`main.py` 不增加业务逻辑。

## 并发、失败与清理

- 单个文件失败不阻塞其他文件继续处理。
- 同一文件同一阶段禁止重复触发。
- 解析、分析、分块和索引分别显示真实状态，不使用笼统的“处理中”。
- AI 分析失败时保留正文和手工填写路径。
- 最终索引失败时保留预览、元数据和分块，允许单项重试。
- 关闭尚有任务运行的弹窗前明确确认；确认关闭后取消未开始任务，并删除已经创建但尚未入库的预览。
- 清理失败不阻塞关闭，但记录失败项；现有预览过期清理继续兜底。
- 成功项从待提交列表锁定，防止重复入库。

## 可访问性与响应式要求

- 文件输入支持键盘操作并保留原生多选能力。
- 每行状态使用文字和图标表达，不能只依赖颜色。
- 状态汇总使用 `aria-live` 低频播报，避免每个进度变化都打断屏幕阅读器。
- 错误信息与对应文件行关联，详情打开后焦点进入标题，关闭后返回原行。
- 窄屏将表格降级为卡片列表，不产生嵌套横向滚动。
- 长文件名可换行或省略展示，但完整名称可通过可访问文本获取。
- 进行中的按钮保持尺寸稳定并防止重复点击。

## 验证范围

### 前端自动检查

- 多文件选择会建立独立任务项，并保留从目录入口带入的默认目录。
- 固定并发上限生效，单项失败不阻塞队列。
- 系统按可验证规则区分 `ready`、`needs-review` 和 `failed`。
- `ready` 默认勾选，异常项默认不勾选。
- 批量修改目录和用途只影响选中项。
- 修改用途导致索引策略变化时，使旧分块预览失效并重新生成。
- 已成功项不会被重复提交，失败项可以单独重试。
- 关闭任务会清理所有未入库预览。

### 后端自动检查

- 现有单文件解析、AI 分析、分块和索引合同保持兼容。
- 空目录 `categoryId` 可以入库，目录不存在仍返回明确错误。
- `draft` 文档不进入模板或正文检索，`effective` 文档可以检索。
- 目录修改不会改变正文和分块记录。

### 浏览器验收

- 分别从知识库首页和具体目录启动批量上传。
- 使用普通参考文档、空白模板、已签合同以及一个无法解析文件组成混合批次。
- 检查正常项默认选中、异常项优先提示、详情编辑、单项重试和部分成功。
- 在审核中创建目录并确认返回后自动选中。
- 验证取消清理、键盘操作、200% 缩放和窄屏布局。
- 验证单文件精细入库流程没有退化。

## 发布与回退

本阶段不迁移数据库数据，不新增外部依赖。上线后旧的单文件入库接口和已入库文档保持兼容。

若批量界面出现问题，可以隐藏批量入口并继续使用原单文件流程；后端单文件接口和知识数据不需要回退。批量处理中已经成功入库的文档视为正常提交，不自动删除。

## 后续升级触发条件

- 需要关闭浏览器后继续处理或恢复任务：增加持久化 `IngestionJob` 和任务执行器。
- 同一原始文件要关联多个检索空间：拆分 `FileAsset` 与 `Document`。
- 不同业务空间需要不同权限、Embedding 或检索配置：增加 `KnowledgeBase`。
- 需要比较、回滚或灰度切换索引：增加 `IndexVersion`。
- 需要按产品、地区、年份等多维筛选：设计独立 Tag/Metadata 模型。
