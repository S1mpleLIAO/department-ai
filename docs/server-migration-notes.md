# 迁移服务器的范围评估

本轮仅评估，未执行迁移。依据现有部署及个人实例运行方式。

## 整套迁移
如果部门后端/前端、PostgreSQL/pgvector、Docling、Harness与个人实例一起迁到新Linux服务器，业务代码通常无需重写。
工作重点是安装相同运行环境、迁移数据库及持久化资料、设置路径、反向代理/证书和切换域名。
需保留数据库中的账号/公司/权限/审核关系、原始文档与技能资源、每人每空间DSH_HOME及工作区、session-authorizations.json。
不应复制正在写入的数据库目录；安排一致性备份/恢复与必要的短暂停写，并验证记录数、下载、检索和登录隔离。
个人任务先运行结束，再停止旧实例并迁移个人持久化状态，避免同时写同一份会话。
Node/Harness挂载根目录、数据目录、skills目录、模型出口与服务URL均须按新环境核对；现有默认路径含/root/liao，不能仅复制代码就认为部署完成。
Harness依赖/原生构建需匹配目标CPU架构，目标不是同架构Linux时另做兼容验证。
验收后再切换域名或代理；旧机保持可回退，在确认稳定后再清理。生产/验收数据库和状态目录继续分开。
具体工期取决于数据量、带宽、CPU架构、模型/解析服务范围、域名切换方式及停机窗口，当前不承诺小时数。

## 只迁计算服务
Docling、Embedding/Rerank/元数据模型已通过服务URL调用，通常能单独迁出并更新地址，但需检查网络连通、认证和时延。
只把个人Harness容器放到另一台机器工作量更大：现实现依赖本机Docker、只读绑定挂载、私有Unix Socket工具/模型桥和监督锁。
需要另行设计远程运行节点、安全通信、存储归属和节点故障恢复，不能把DOCKER_HOST换成远程地址直接上线。

## 资源判断
CPU更好主要帮助并发冷启动与本地解析。外部模型的响应速度还取决于模型服务和网络。
本次4实例合成测试约80–83秒同时冷启动，CPU短时峰值94%；运行实例内存约380–396MiB，仍有至少2321.5MiB可用内存。
这些结果不覆盖并发OCR或重脚本。当前磁盘约92%使用，迁移方案必须同时处理磁盘容量与持续数据增长，不能只比较CPU。
实例上限限制运行资源；空闲回收保留会话/文件，因此不会自动释放历史资料磁盘。
